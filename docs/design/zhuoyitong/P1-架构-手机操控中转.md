# P1 架构方案：手机操控经 Mac 中转

基线：dsh-go `main` 8fe1c1c，引擎 DSH 0.2.1-rc.4，目标机 HUAWEI Pura X（VDE-AL00，HarmonyOS 7.0.0.109）卓易通容器。日期：2026年11月02日。

证据标记：〔读码〕读了源文件；〔实测〕本次在本机或真机执行并看到输出；〔推断〕由前两者推出、未执行；NOT_RUN 未做。〔P0A〕〔P0B〕〔P0C〕引用前序报告章节，〔引擎〕引用 `P1-架构-引擎.md`。引用格式 `文件:行号`，Kotlin 文件省略目录 `app/android/app/src/main/kotlin/io/github/ccch1mneyyy/dsh_app/phone/`。

## 0. 结论

1. 选 B：保留 DSH Go 现有的 stdio 中继、`PhoneBridge`、`McpServer`、`PhoneCore`、`SafetyGate` 与固定工具集，只把「手」换掉。新增 `MacRelayDriver`（实现 `PhoneDriver`，`PhoneContracts.kt:123`）顶替无障碍驱动，新增 `RelaySystemApi`（包装 `SystemApi`，`SystemApi.kt:23`）处理鸿蒙应用的列表与拉起。Mac 中继是一个只做设备原语的 HTTPS 服务，不是 MCP 服务器。
2. 引擎看到的工具与现在逐字相同（13 个，`PhoneToolCatalog.kt:12-24`），元素编号、屏幕号、确认卡、交还用户、操作记录、停止语义全部沿用。不新增 `wait` 工具：每个动作返回的都是动作稳定后的新屏幕，且工具定义变动会使 DeepSeek 的 KV 缓存从第一个变动 token 起失效（`PhoneToolCatalog.kt:5-10`）。
3. 控件树由中继做格式转换（鸿蒙 `dumpLayout` JSON → 去噪的节点树），文字化、编号、打码、敏感标记仍由 Kotlin 的 `ScreenFormat` 完成（`a11y/ScreenFormat.kt:119`，纯 Kotlin，输入是 `a11y/UiTree.kt:41` 的 `UiNode`）。同一份规则只有一个实现。
4. 硬规则（密码/验证码/付款/系统设置/不碰名单）留在 Kotlin 侧拦，中继不重复实现。理由是确认卡、交还、解除限制、任务生命周期都在 App 里，中继侧再写一套就是第二份会漂移的规则。中继只保留与任务无关的底线：来源地址、令牌、命令注入防护、速率、暂停开关。
5. 悬浮胶囊在容器里浮到鸿蒙界面上这件事没有证据，且它依赖的无障碍悬浮窗在本机启用不了（〔P0B 9.2〕）。方案不依赖悬浮窗：确认与交还走「通知 → 把 App 拉到前台出卡 → 退回对话里问」三级链（第 3 节），停止走通知按钮、App 内按钮、Mac 端 `halt`。三级链的前两级需要真机探针确认（P2-d1）。
6. Mac 侧用 Node（零依赖），launchd 常驻，标签 `com.albert.dsh-relay`，端口 8731，HTTPS 自签证书加指纹钉扎，配对用 Mac 终端显示的一次性配对码，令牌不进聊天、不进剪贴板。
7. 每个动作多一次「执行前复核」读屏（实测单次读屏约 1.4 秒），一步操作约 4 秒，比安卓真机慢。换来的是不会点到已变化的界面。
8. 待拍板 2 条（第 11 节）。

## 1. 口径与边界

已钉死（00-改造方案 第一、二节，2026年11月02日修订）：

- 操控的「手」经 Mac 中转，Mac 必须在线；手机上的引擎发看屏/点按请求，Mac 上常驻的 hdc 中继用官方 hdc 客户端（`~/.local/bin/hdc` 3.1.0e，server 常驻 `127.0.0.1:8710`）经无线调试或 USB 操作手机。
- 命令集：`snapshot_display` 截屏，`uitest dumpLayout` 读控件树，`uitest uiInput click/doubleClick/longClick/swipe/drag/fling/inputText/text/keyEvent` 操作，`aa start` 拉应用。这些命令对鸿蒙原生界面和容器里的安卓界面都有效（〔P0B 9.2〕末段：容器 Activity 在 uitest 窗口树里是一级窗口）。
- 本期不做不打扰模式（后台虚拟屏）。原因是 uitest 只作用于物理屏。因此 `open` 的 `background:true`、`screen` 的 `background:true` 在 Mac 模式下返回固定的「本机不支持后台屏」说明（沿用 `PhoneEnv.backgroundUnavailable()`，`PhoneCore.kt:17`）。
- P0-C 规划的 Kotlin 版 HDC 客户端（约 3 人天，〔P0C 5〕）整项取消，由官方 hdc 在 Mac 上承担。`tooling/hdc-poc/` 保留作将来鸿蒙原生版的参考。

## 2. 主要矛盾与接法选择

主要矛盾：手机操控分两层，上层（工具集、元素编号、安全规则、确认、任务生命周期、操作记录）与 OS 无关，下层（读屏与注入输入）与 OS 绑定。卓易通里下层只能经 Mac 取得。方案要让上层一行不改地复用，只替换下层。

### 2.1 比较

| 比较点 | A：Mac 中继本身是 MCP 服务器，引擎经 streamable-http 直连 | B：保留 PhoneGuest stdio 中继与 Kotlin 桥，底层通道换成 HTTPS 调 Mac 中继 |
|---|---|---|
| 硬规则落在哪 | 引擎直接打到 Mac，绕过 App，`SafetyGate`、`PhoneTasks`、确认卡、解除限制、操作记录全部不经过；要保留就得在 Node 里重写一遍，确认还得回调手机，而手机上没有可被 Mac 回调的服务 | 不变。`PhoneCore.execute` → `SafetyGate` → 驱动，与安卓同一条路径（`PhoneCore.kt:69-151`） |
| 工具集稳定性 | `tools/list` 由 Mac 返回，Mac 离线时工具消失或变化，违反「工具集固定、不随权限状态变」的缓存纪律（`PhoneToolCatalog.kt:5-10`） | 工具集仍是 Kotlin 常量，JVM 测试钉哈希；Mac 离线只让调用返回可执行的说明 |
| 凭据暴露面 | Mac 令牌与地址写进引擎配置（overlay YAML，引擎和它的 shell 工具都读得到），提示注入后的模型可直接用 Node 打 Mac | 令牌只在 App 私有文件（0600，先例 `background/AdbKeyStore.kt:14-24`），引擎只持有本地桥的每次启动令牌。同 uid 代码读得到私有文件，这一点两案相同，B 多一道跳 |
| 现有 UI 能否复用 | 悬浮条、确认卡、停止都依赖 App 内事件，A 里没有事件源 | 复用 `PhonePrompts` 的三级展示（浮层 → 通知 → App 内弹窗，`PhonePrompts.kt:107-126`），无障碍浮层不存在时它已经能工作 |
| 改动面 | Kotlin 几乎不动；Mac 侧要实现 MCP、13 个工具、元素编号、屏幕格式、安全规则、确认协议 | Kotlin 新增约 6 个文件、改 4 个；Mac 侧只实现设备原语和鉴权 |
| 离线/断线 | 引擎 MCP 客户端的重连与启动失败行为不可控（`failOnStartupError:false` 下工具直接缺席，〔P0A 1.6〕） | 驱动返回 `Availability(false, reason)`，`PhoneCore.driverFor` 把原因交给模型（`PhoneCore.kt:338-350`），App 可发修复通知，中继恢复后下一次调用即通，不用重启引擎 |
| 与安卓真机代码路径的隔离度 | 低：两套工具实现并存，语义会漂移 | 高：`PhoneControl.driver()` 按「手」选驱动，其余路径同一份；安卓真机行为不变 |
| 与引擎线接口 | 需要在引擎配置里新增 MCP 服务器条目，与 `PhoneGuest.PATCH_YAML` 互斥 | 引擎线已按「stdio 中继沿用、路径换物理路径」设计（〔引擎〕1、3.7），零接口增量 |

A 成立的前提是 Mac 侧可以独立裁决一切安全问题。这里不成立：确认要问的人在手机上。

## 3. 悬浮条、确认卡、停止在容器里的处境

问题：安卓上的操控 UI 是无障碍悬浮窗（`a11y/ControlOverlay.kt`），容器里能否浮在鸿蒙界面上。

证据：

- 无障碍悬浮窗不可用。容器的无障碍服务列表为空，启用页打不开（〔P0B 9.2〕实测），`PhoneRegistry.overlayGate` 因此永远为 null。
- 普通悬浮窗（`TYPE_APPLICATION_OVERLAY`）无任何探针数据，NOT_RUN。〔推断〕容器的每个 Activity 在宿主侧是一个一级窗口（〔P0B 9.2〕），容器内浮层属于容器自己的合成面，不能期待它盖在鸿蒙原生应用之上。
- 通知是否出现在鸿蒙一侧、按钮能否回调到容器内的广播接收器：NOT_RUN。
- 容器内 App 能把自己拉到前台：〔P0B 9〕里 `ACTION_APPLICATION_DETAILS_SETTINGS` 从探针 Activity（前台）启动成功，从后台服务启动未测。

对策：确认与交还不依赖浮层。`PhonePrompts.schedule` 的现有顺序是「浮层 → 通知 → App 内弹窗」（`PhonePrompts.kt:107-126`），无浮层时自动落到通知，通知展示不了时自动把 App 拉到前台出弹窗，仍不行返回 `Decision.UNAVAILABLE`，`SafetyGate` 把它变成「请用户打开 DSH Go 检查通知」并停手（`SafetyGate.kt:312-316`）。Mac 模式在这条链上加一级：中继提供 `POST /v1/launch`，Kotlin 在 Activity 拉前台失败时请 Mac 用 `aa start -b <DSH Go 包名> -a <MainActivity>` 把 DSH Go 拉到前台（〔推断〕容器应用在宿主侧有 bundle/ability 名，〔P0B 9.2〕uitest 里是 `probe.zyt / probe.zyt.MainActivity`；`aa start` 对容器应用是否可用 NOT_RUN，纳入 P2-d1）。

交还（`handoff`）的难点在于用户要去操作目标应用，卡片在 DSH Go 里就看不到目标。因此交还优先通知（带「继续/停止」按钮，`NotificationGate.kt:12-17`），通知不可用时才拉 App 弹窗，并在卡片里写明「操作完回到这里点继续」。

停止的四个入口：通知上的「停止操作」（已有，`docs/guide/zh/04-phone-control.md` 停止一节）、手机操控页「正在操作手机」卡的停止、对话里中断、Mac 端 `dsh-relay halt`。前三个经 `PhoneTasks.stop` 取消 `SerialWorker` 并向中继发 `POST /v1/stop` 掐断在途命令；第四个独立于手机，是 Mac 侧的总闸。

需要真机探针确认的三项（P2-d1）：S-OVL 普通悬浮窗能否盖在鸿蒙原生界面上；S-NTF 容器通知是否弹出且按钮广播能回到容器；S-FGS 后台服务 `startActivity` 与中继 `aa start` 能否把容器应用拉前台。S-NTF 和 S-FGS 都失败时，确认退化为「在对话里问」，此时默认确认方式「每次都询问」会让带敏感词的步骤全部被拒，用户需要改成「本任务免确认」或「始终免确认」才能继续（第 11 节拍板项 1 相关）。

## 4. 中继接口 v1

### 4.1 总则

- 传输：HTTPS，JSON 请求体与响应体，UTF-8。证书为中继自签 ECDSA P-256，客户端钉扎叶证书 SHA-256。回环地址 `127.0.0.1` 另开明文 HTTP 监听，仅供本机 CLI 与测试。
- 鉴权头：`Authorization: Bearer <token>`；所有请求必须带 `X-Dsh-Relay: 1`（浏览器跨站请求带不出自定义头，先例 figma-eye `CLAUDE.md` 红线一条）。不返回任何 CORS 头。`Host` 只接受 IP 字面量和配置里的名字。
- 请求标识：`X-Request-Id`（UUID）。写动作按它幂等，60 秒内同 id 重放返回首次结果，在途时返回 `202`+`in_progress`。因此客户端网络读超时后可以带同一 id 重试一次，不会点两次。
- 任务标识：`X-Dsh-Task: <taskId>`（`PhoneTasks` 的任务号）。`POST /v1/stop {task}` 取消该任务在途与排队的命令。
- 来源限制：只接受回环、RFC1918、`100.64.0.0/10`（Tailscale）；其余 403。
- 失败限速：同一来源 IP 每分钟 5 次鉴权失败后封 60 秒（429）。

### 4.2 端点

| 方法 路径 | 鉴权 | 作用 | 请求 | 响应要点 |
|---|---|---|---|---|
| GET `/v1/ping` | 否 | 区分「地址错」与「令牌错」 | 无 | `{service:"dsh-relay", v:1}` |
| POST `/v1/pair` | 配对码 | 首配 | 见 5.5 | `{token, serverProof}` |
| GET `/v1/device` | 是 | 设备与中继状态（读缓存，不碰设备） | 无 | `{halted, device:{state, via, target, model, since, locked, screenOn}, queue:{depth}, version}` |
| POST `/v1/observe` | 是 | 读屏 | `{image?:bool, bundle?:string, timeoutMs?:int}` | 见 4.3 |
| POST `/v1/act` | 是 | 注入输入 | `{op, ...}` 见 4.4 | `{ok, op, steps:[{cmd, ms, out}], tookMs}` |
| POST `/v1/launch` | 是 | 拉起应用 | `{bundle, ability?, module?}` | `{ok, resolved:{module, ability}, out}` |
| GET `/v1/apps` | 是 | 鸿蒙应用清单 | `?q=` | `{apps:[{bundle, label|null, alias|null}]}` |
| POST `/v1/target` | 是 | 手机端更新无线调试地址 | `{addr:"192.168.31.226:46225"}` | `{ok, state}`；地址必须是私网 IPv4，端口 1024–65535，其余 422 |
| POST `/v1/stop` | 是 | 取消任务在途命令 | `{task}` | `{cancelled:n}` |
| POST `/v1/halt` | 是 | 手机侧急停（只能停，不能恢复） | 无 | `{halted:true}` |
| POST `/ctl/resume` `/ctl/pair` `/ctl/revoke` `/ctl/target` | 本机管理令牌 | 仅回环监听，CLI 使用 | | |

「只能停不能恢复」是有意的不对称：令牌泄漏的最坏结果是中继被停，不是被放开。

### 4.3 observe

命令：`uitest dumpLayout -p /data/local/tmp/dsh-relay/l-<seq>.json`，再 `hdc file recv` 取回，立即 `rm` 设备端文件。要截图时再 `snapshot_display -f /data/local/tmp/dsh-relay/s-<seq>.jpeg`，同样取回即删。设备端目录首次使用时创建。

中继对原始 dump 做的裁剪（不做文字化）：

- 丢弃 `visible:false`、零面积、`opacity` 为 0 的节点；丢弃 `backgroundColor/blur/clip/zIndex/hashcode/hierarchy/origBounds` 等渲染属性。〔实测〕原始 dump 每节点 27 个字段，裁剪后每节点 6–10 个，预期体积降到约 1/4。
- 合并只有一个子节点且无文字无标志的纯容器（`Stack/Row/Column/RelativeContainer/FrameLayout`），保留 bounds 取子节点。
- 单次响应超过 600 KB 时按面积从小到大丢叶子节点，置 `truncated:true`。
- 鸿蒙 `type` → `cls/role` 的映射是一张配置表 `~/.dsh-relay/typemap.json`（随仓库带默认值）：`Button→android.widget.Button/button`，`Toggle→android.widget.Switch/switch`，`Checkbox→CheckBox/checkbox`，`Radio→RadioButton/radio`，`Slider→SeekBar/slider`，`Select→Spinner/combobox`，`TextInput/TextArea/Search→android.widget.EditText` 且加 `editable`，`List/Grid/Scroll/WaterFlow→androidx.recyclerview.widget.RecyclerView` 且加 `scroll`，`Tabs/TabBar/TabContent→TabWidget/tab`，`Image→android.widget.ImageView`，`Text→android.widget.TextView`。表是〔推断〕：本次 dump 的 117 个节点来自探针 App，只含容器安卓控件（`android.widget.TextView` 26、`android.widget.Button` 7）和 ArkUI 的 `Stack/Row/SymbolGlyph/Image/RelativeContainer`，没有 `Toggle/TextInput/List` 实例。P2-0 在设置页、Wi-Fi 密码框上抓夹具后修正此表。
- 滚动方向：dump 里只有 `scrollable` 布尔值，中继给 `scroll` 标志位置全方向，`ScreenFormat` 会写「可下滑」，可能与实际不符，由驱动在 `scroll` 动作后用读屏变化判断是否到底（沿用 `MainScreenDriver.scroll` 的做法，`a11y/MainScreenDriver.kt:398`）。
- 密码框：dump 没有密码标志，`uitest dumpLayout -e` 只接受 `uniqueId`（〔实测〕「Invalid attribute name, currently supported names are 'uniqueId'」）。中继对可编辑节点只在 `hint/desc/text` 命中密码类词、或文本全是 `•`/`*` 时置 `password`；漏判由 Kotlin 侧附近标签识别与系统页硬规则兜底，是第 7 节的已知缺口，P2-0 与 P2-d2 用真实密码框验证。

### 4.4 act

所有坐标是显示器像素，整数，范围检查 `0 ≤ x < width`，越界 422。

| op | 参数 | 设备命令（每条都作为一步记录） |
|---|---|---|
| click / doubleClick / longClick | `x,y` | `uitest uiInput click\|doubleClick\|longClick X Y` |
| swipe | `x1,y1,x2,y2,velocity?`（200–40000，默认 600） | `uitest uiInput swipe X1 Y1 X2 Y2 V` |
| fling | 同上加 `stepLength?` | `uitest uiInput fling ...` |
| key | `name`：`back` `home` `enter` `recents` `notifications` | `back/home` → `uitest uiInput keyEvent Back\|Home`；`enter` → keyEvent 2054；`recents` `notifications` 由 `gestures.json` 里的滑动脚本实现（屏幕高宽由 dump 的 display 得出，默认：recents 为底边中点上滑并停留，notifications 为顶边左侧下滑） |
| text | `text` | `uitest uiInput text '<text>'`（向当前焦点输入） |
| replaceText | `x,y,text,commit?` | `click x y` → 150 ms → `keyEvent 2072 2017`（全选）→ `keyEvent 2055`（删除）→ `text '<text>'`；`commit:true` 时再 `keyEvent 2054`（回车，提交拼音组词条），默认不发（P5 RC-F3：单行框里回车等于发送） |

键码表在 `keymap.json`：HOME=1 BACK=2 ENTER=2054 DEL=2055 CTRL_LEFT=2072 A=2017，〔推断〕来自 OpenHarmony 键码定义，`Back/Home` 两个名字〔实测〕在 help 里被接受；其余键码 P2-a 上机逐个验证。`inputText` 命令不使用：它会追加还是替换〔未知〕，用 `replaceText` 宏加 Kotlin 侧读回比对（沿用安卓驱动的读回逻辑，`a11y/MainScreenDriver.kt:546-566`）替代。

命令注入防护（硬要求）：

- 中继永不拼接本机 shell 字符串；用 `child_process.execFile(HDC, ['-t', target, 'shell', cmd])`。`cmd` 在设备端被 shell 解释，因此所有数字参数先 `Number.isInteger` 校验，文本参数做单引号转义（`'` → `'\''`），拒绝 NUL 与除 `\n` 外的控制字符，`\n` 在 `text` 里拒绝（回车用 `key enter`），长度上限 500 字符。
- 验收用例（第 8 节 R10）：`a'b"c$(id);d\`e` 与中文各输入一次，设备上收到的是原文，无副作用。

响应里 `steps[].out` 是命令回显（`No Error` 表示成功，〔实测〕`keyEvent Back` 的回显，〔P0C 4〕）；回显不是 `No Error` 或 hdc 退出码非 0 时 `ok:false`，错误码 `command_failed`。

### 4.5 launch、apps

`launch`：未给 `ability` 时用缓存的 `bm dump -n <bundle>` 取入口模块的 `mainAbility`（〔实测〕`com.huawei.hmos.settings` 的 `hapModuleInfos[0].mainAbility` 为 `com.huawei.hmos.settings.MainAbility`，`mainEntry` 为 `phone_settings`），命令 `aa start -b <bundle> -a <ability> -m <module>`；不接受 `uri`（P4 M4 删除：App 不用，任意 scheme 会入日志，中继对带 `uri` 的请求回 422）。设备锁屏时 `aa start` 报 10106102（〔P0B 11〕备注，实测），映射为 `device_locked`。

`apps`：`bm dump -a` 的输出是按用户分组的缩进列表（`ID: 100:` 下每行一个包名，〔实测〕264 行）。`bm dump -n` 的 `label` 是资源引用（`$string:settings_title`，〔实测〕），取不到人读名称，所以中继带一张别名表 `aliases.json`（设置→`com.huawei.hmos.settings`、应用商店、相机、图库、浏览器等约 30 项，用户可加），`label` 字段取别名，没有则为 null。`RelaySystemApi.apps()` 合并容器应用与这份清单，以包名为键。

### 4.6 错误码

响应统一为 `{ok:false, error:{code, message, retryable, hint?}}`。

| HTTP | code | 含义 | Kotlin 侧对模型的说法（`l10n:keep agent tool result` 中文字面量） |
|---|---|---|---|
| 401 | `unauthorized` | 令牌无效或被撤销 | 需要用户在 设置 → 手机操控 重新配对 |
| 403 | `forbidden_source` | 来源地址不在允许范围 | 同上，提示检查网络 |
| 409 | `cancelled` | 任务已被停止 | 沿用 `PhoneTasks.STOPPED_MESSAGE` |
| 409 | `device_locked` | 手机锁屏 | 沿用 `PhoneCore.locked` 的说明（`PhoneCore.kt` 的 `locked()`） |
| 422 | `bad_args` | 参数越界或含非法字符 | 内部错误，写日志 |
| 423 | `halted` | Mac 端已暂停 | Mac 上的中继被暂停，请用户在 Mac 上 `dsh-relay resume` |
| 424 | `command_failed` | uitest/aa 回显非成功 | 带回显首行 |
| 429 | `busy` | 队列满（深度 4） | 前面的操作还没结束，稍后再试 |
| 503 | `device_offline` | 中继在线但连不上手机 | 手机无线调试断了或端口变了：在 设置 → 手机操控 更新端口，或插 USB |
| 503 | `device_unauthorized` | 手机未授权这台 Mac | 请用户在手机上点「允许」 |
| 504 | `device_timeout` | 设备命令超时 | 这一步可能执行了也可能没有，先 screen |
| 500 | `internal` | 中继内部错误 | 带 request id |

Kotlin 把「连不上中继」（连接超时、拒绝、证书指纹不符）单独标为 `relay_unreachable`，不是中继返回的码。证书指纹不符按 `unauthorized` 同等处理并要求重新配对，不静默降级。

### 4.7 超时、并发、排队

| 项 | 值 |
|---|---|
| Kotlin 连接超时 | 3 s |
| 读屏 | 中继内 8 s（布局 5 s + 截图 3 s）；Kotlin 读超时 10 s |
| 动作 | 中继内 5 s；Kotlin 读超时 8 s |
| launch | 中继内 8 s |
| 队列 | 全局串行，同一时刻只有一条设备命令在跑；深度 4，满则 429；任务被 stop 时在途命令的 hdc 子进程被杀，排队项返回 `cancelled` |
| 读操作重试 | 中继对 `observe` 在设备超时后重连一次再试；Kotlin 对 `observe` 网络错误重试一次 |
| 写操作重试 | 中继永不自动重试；Kotlin 仅在没收到响应时用同一 `X-Request-Id` 重发一次 |

单设备串行的依据：`uitest` 注入与读屏同时进行会读到动作中途的树，且多个 `uitest` 进程同时存在的行为未测〔推断〕。

### 4.8 目标设备选择与重连

输入：`hdc list targets -v`（〔实测〕当前同时列出 `192.168.31.226:46225 TCP Connected` 与 USB 序列号 `<USB序列号>`）。

1. 默认优先 USB：USB 线在位时稳定且不受 Wi-Fi 省电影响；`device.prefer` 可配 `usb|tcp|auto`，多台 USB 设备时必须配 `device.serial`。
2. 没有 USB 时用 TCP 目标。目标来源三处，按序取：`POST /v1/target`（手机端设置页填的），CLI `dsh-relay target set`，USB 在位时自学：`hdc -t <usb> shell "param get persist.hdc.port"` 取端口，`ifconfig wlan0` 取手机 IP（两条命令〔P0C 3〕与〔P0B 9.1〕里均已在真机跑通）。
3. 在线判定：每次选定目标后 `hdc -t X shell "echo ok"`，3 秒内回显才算在线。TCP 超时后先 `hdc tconn <addr>` 再重试；〔P0C 4〕观察到 Wi-Fi 省电休眠会让 `connect` 超时约 10 秒、几十秒后自愈，所以 TCP 的退避序列是 2、4、8、15、30 秒，期间对外状态为 `connecting`，请求直接得到 `device_offline`+`retryable:true`，不排队等待。
4. 活跃期保活：最近 120 秒内有请求时每 5 秒做一次 `echo ok` 心跳（顺带抑制手机 Wi-Fi 休眠），空闲时每 30 秒查一次 `list targets`，不碰设备。
5. 无线调试端口每次开关可能变（〔P0C 3〕）。变了以后的恢复路径：USB 在位则第 2 步自动学到；否则用户在手机上读到新端口，填到「手机操控」页的「无线调试地址」，App 调 `POST /v1/target`。手机 UDP 发现（8710）的报文格式没有查清（〔P0B 5〕〔P0C〕均无应答），不依赖它。
6. `device_unauthorized`：hdc 回报 `[E000002]` 一类未授权文案时映射，等待用户在手机上允许（〔P0C 2.3〕第 4 步）。Mac 的 hdc 密钥 `~/.harmony/hdckey` 已被手机「始终允许」，正常不会出现。

### 4.9 日志与脱敏

位置 `~/Library/Logs/dsh-relay/relay.log`，每行一个 JSON，按 10 MB 滚动保留 5 份。字段：

```
{"ts":"2026-11-02T10:31:07.412+08:00","req":"3f1c…","task":"41","ip":"192.168.31.226","tok":"a1b2c3",
 "kind":"act","op":"click","args":{"x":660,"y":1020},"cmd":"uitest uiInput click 660 1020",

```

- 记：时间、请求 id、任务号、来源 IP、令牌短标识（令牌哈希前 6 位）、种类（read/act/launch/auth/ctl）、动作、坐标、实际发往设备的命令、耗时、结果码。
- 不记：控件树文字、图片、`text/replaceText` 的文字内容（命令里文本位替换为 `<text:12 chars>`；`logText:true` 配置项默认关）、令牌、配对码。
- 不落盘：截图与布局 JSON 只在内存和设备临时目录存在，取回后设备端立即 `rm`，Mac 端不写文件。

### 5.2 进程模型

单进程单事件循环。设备命令走一条 FIFO 队列，每条命令起一个 `hdc` 子进程（约 50 ms 启动成本，hdc server 常驻复用）。子进程带超时与取消，取消时 `SIGKILL`。设备端临时文件目录 `/data/local/tmp/dsh-relay/`。

hdc server 在 `127.0.0.1:8710` 是共享的，用户在终端里手敲 `hdc` 与中继用的是同一个 server。launchd 配置 `AbandonProcessGroup` 为真，中继重启时不连带杀掉 hdc server。

### 5.3 监听

- 不绑 `0.0.0.0`。启动时枚举 `os.networkInterfaces()`，监听：每个私网 IPv4（本机 `en0` 为 192.168.31.182，〔实测〕）、`100.64.0.0/10` 的 Tailscale 地址（当前 tailscaled 未运行，〔实测〕`tailscale ip` 失败）、`127.0.0.1`。不监听 `198.18.0.0/15`（本机 `utun` 代理网段，〔实测〕198.18.0.1）。
- 每 15 秒重新枚举，地址变化时重绑，DHCP 换地址后无需重启。
- 端口 8731（〔实测〕当前空闲），`DSH_RELAY_PORT` 可改。测试用 38731 且 `DSH_RELAY_HOME` 指向临时目录，避免碰到用户的真实实例。

### 5.5 令牌与首配（令牌不出现在聊天与剪贴板）

文件（`~/.dsh-relay/`，目录 0700，文件 0600）：`tls/key.pem`、`tls/cert.pem`、`tokens.json`（只存令牌 SHA-256、名称、创建时间、最近来源与时间）、`control.token`（本机管理令牌，CLI 用）、`config.json`。证书由中继首次启动时用系统自带 `/usr/bin/openssl`（〔实测〕存在）生成（`install.sh` 不生成；P5 起重新生成会写 `cert_regenerated` 日志行）：`req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes -days 3650 -subj /CN=dsh-relay`。

首配流程：

1. Mac 终端执行 `dsh-relay pair`。命令生成 10 位 Crockford base32 配对码（约 50 位熵），5 分钟有效，最多验证 5 次，成功一次即作废，并打印本机可用地址（`192.168.31.182:8731`、Tailscale 地址）。配对码只显示在终端，不写文件、不写日志。
2. 手机上 设置 → 手机操控 → 准备 → Mac 中继 → 配对，填地址和配对码。App（Kotlin）向 `POST /v1/pair` 发起 TLS 连接，此时尚未信任证书，记下握手看到的叶证书指纹 `seenFp`。
3. 客户端生成 16 字节随机数 `nonce`，计算 `key = PBKDF2-HMAC-SHA256(code, salt=nonce, 200000 次, 32 字节)`，`proof = HMAC-SHA256(key, "pair|" + seenFp)`，发送 `{nonce, seenFp, proof, name}`，配对码本身不上线。
4. 中继用自己的真实指纹 `fp` 重算期望值，不等则拒绝并计入尝试次数。相等才签发令牌（32 字节随机，base64url），回 `{token, serverProof = HMAC-SHA256(key, "srv|" + fp)}`。
5. 客户端校验 `serverProof`，通过才把 `{addr, fp, token}` 写入 App 私有文件 `filesDir/phone-relay/relay.json`（0600）并从此钉扎 `fp`。

这套流程挡的是同一局域网里的中间人：他在 TLS 里换证书，`seenFp` 与真实指纹不同，没有配对码就算不出一致的证明；PBKDF2 的 20 万次迭代让离线穷举配对码不可行。令牌永远在已钉扎的 TLS 里传输，不进 Dart 层，不进日志，不进剪贴板。

撤销：`dsh-relay revoke <id|all>`；手机端「忘记这台 Mac」只删本地文件，Mac 端令牌需另行撤销，页面提示这一点。

### 5.6 CLI 与健康检查

`dsh-relay status`（设备状态、队列、令牌列表、最近错误）、`pair`、`revoke`、`halt`（写 `~/.dsh-relay/HALT` 标志并立即取消所有在途命令，之后除 `/v1/ping` 与 `/v1/device` 外的请求返回 423）、`resume`、`target show|set <addr>|auto`、`logs [-f]`、`doctor`。

`doctor` 检查：Node 版本；`HDC_BIN` 存在及版本；hdc server 是否应答；`list targets`；证书存在与剩余有效期；各监听地址可绑；`pmset` 睡眠值；launchd 作业已加载；日志目录可写；8731 端口占用者是否是本服务。

## 7. 安全分层

| 规则 | 谁拦 | 理由 |
|---|---|---|
| 密码、验证码、支付密码框不填 | Kotlin：`SafetyGate.isSecretTarget`（`SafetyGate.kt:112`）+ 驱动级 `refuseWrite` | 确认、交还、解除限制都在 Kotlin；规则只写一次 |
| 系统设置/权限/安装器/安全中心 | Kotlin：`SYSTEM_PACKAGES` 与 `ProtectedPages`，补鸿蒙包名后同一条规则覆盖 | 〔实测〕鸿蒙设置是 `com.huawei.hmos.settings`，不补则「打开设置关蓝牙」这类任务在鸿蒙上根本不被当作系统页 |
| 不碰名单、每步确认名单 | Kotlin：`PhonePolicies` | 名单按包名，鸿蒙应用同样按 bundle 名匹配；默认名单里的银行/支付包名是安卓包名，鸿蒙元服务/原生版另有 bundle 名，需要用户在应用名单里补 |
| 敏感词按钮先确认 | Kotlin：`SensitiveWords` | 渲染时标 `⚠`，文本来自鸿蒙控件，规则不变 |
| 来源、令牌、限速、暂停 | 中继 | 与任务无关的网络层底线 |
| 命令注入 | 中继（参数校验与转义）+ Kotlin（文本长度上限） | 文本最终被设备端 shell 解释，必须在拼命令的那一层转义 |
| 任务停止 | Kotlin 取消任务并通知中继杀在途命令；Mac `halt` 作总闸 | 停止要在 2 秒内生效，不能只靠 Kotlin 侧超时 |

已知缺口：

1. 鸿蒙控件树没有密码标志（4.3），中继侧只能按词和掩码字符猜，漏判时模型可能把明文打进密码框。缓解是系统页硬规则（设置里的 Wi-Fi 密码框在 `com.huawei.hmos.settings` 内会被整页拦），其他应用里的登录页靠 `SensitiveWords.secretHit` 的标签词（密码、验证码、PIN）。第三方鸿蒙应用的密码框是否带可识别词需要 P2-d2 实测。
2. 同 uid 代码读得到 `filesDir/phone-relay/relay.json`，提示注入后的模型若用引擎的 shell 工具读取并直接打 Mac，会绕开 App 内的确认。这与现有 `bridge.json` 的信任模型一致（`PhoneBridge.kt` 类注释「Same-uid code … gets past both checks by design」），中继侧的审计日志、速率限制和 `halt` 是事后与总闸，不是预防。

（P5 深度审查后追加，2026年11月02日）
- `/v1/device` 不再只是「读缓存」：`!halted && device.state !== 'ok'` 时异步踢一次 acquire（限频 10 秒），启动后有绑定目标也主动 acquire 一次；手机端门禁只看 halted / unreachable / unauthorized，`device.state` 与 `locked` 只用于界面展示，「测试连接」在 offline 时再查 3 次、每次隔 2 秒。原因：P5 RC-F1，冷启动与掉线后手机端被自己的门禁锁死。
- `device.locked` 带时效：`/v1/device` 只在最近 15 秒内 observe 过时返回 true/false，否则 null；手机端 `isLocked()` 只认最近 15 秒内 observe 的结果；真正的锁屏防线是 observe 里的 `cap.locked`。原因：P5 RC-F2，P4 H2 的修法把缓存当成了实时值。
- `replaceText` 默认不发回车，`commit:true` 才发；手机端先不回车、回读不一致（拼音组词条）才补一次 enter，`submit=true` 在回读一致后发一次。原因：P5 RC-F3，单行输入框里无条件回车等于发送。
- observe 的 `display` 按维度取已见最大值，有截图时以截图尺寸为准；软键盘与半屏窗口不再让它来回跳。原因：P5 RC-F5。
- 中继常驻面：日志写失败不再让进程退出（P5 RS-R1）；HTTPS 全部绑不上时报错退出而非静默 exit 0（RS-R6）；配置与令牌文件损坏时一行报错退出或备份 `.bad`（RS-R7）；hdc 输出累计 8 MB 即 kill（RS-R9）；幂等缓存键绑 method+path+body（RS-R13，收掉 P4 M5）。全表见 `P5-深度审查.md`。
