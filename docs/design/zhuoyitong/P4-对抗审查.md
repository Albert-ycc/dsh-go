### H1 高　中继令牌文件对引擎进程可读，模型的 shell 可以绕过整个 SafetyGate 直接操控手机

- 入口：bionic 引擎是 App 的子进程，与 App 同 uid，没有 PRoot 的根目录隔离。令牌在 `filesDir/phone-relay/relay.json`（0600 对本 uid 无约束）。
- 触发条件：提示注入或恶意插件让模型执行 `cat <filesDir>/phone-relay/relay.json`（路径从 `HOME=<filesDir>/runtime-bionic/rootfs/root` 向上两级可得），再用 Node 的 `fetch` 带令牌、钉自己读到的指纹，直接 POST Mac 中继的 `/v1/act`、`/v1/observe`、`/v1/launch`。
- 实际影响：SafetyGate 的删除确认、DEFAULT_DENY、系统页只看不动、密码框拒填、「DSH 自己的界面不操作」全部在 App 进程内，中继侧没有任何同等检查，所以全部被绕过。`AGENTS.md`「凭据与隐私」承诺令牌「只存 App 私有目录（0600）」，在 glibc/PRoot 世界成立（令牌在 rootfs 外），在 bionic 世界等于对引擎公开。同理 `phone-adb/` 里的自连 ADB 私钥。〔推断〕未在真机上演示，但 `BionicLaunch.plan` 的 cwd、环境、argv 里没有任何隔离措施。
- 最小修法：令牌用 Android Keystore 的 AES-GCM 密钥加密后落盘（Node 子进程调不了 Keystore，读到的只是密文）；解密只在 `RelayClient` 的 Kotlin 进程内做。同时把「令牌可被引擎读取」写进 AGENTS.md 的例外说明，直到修完。
- 证据：`phone/PhoneControl.kt:66`（`File(app.filesDir, "phone-relay")`）；`runtime/BionicLaunch.kt:59-71`（HOME、cwd 在 `filesDir/runtime-bionic/rootfs/root`，无隔离）；`phone/relay/RelayTokenStore.kt:36-50`（明文 JSON）。

### M1 中　`replaceText` 在没有确认焦点的情况下发 Ctrl+A、Delete

- 入口：`type` 工具。
- 触发条件：`lib/acts.mjs:107-115` 的四步（点击、Ctrl+A、Delete、输入）之间没有读屏；点击落点在读屏后到 `act` 前发生了界面变化（弹窗、列表重排），或节点被误分类为可编辑。
- 实际影响：〔推断〕Ctrl+A 全选后 Delete 作用在非输入框上，在文件管理器或相册这类页面是批量删除；超时在第三步后发生则输入框被清空而新文本未输入，且结果被幂等缓存 60 秒（`executed: true`）。

- 证据：`lib/acts.mjs:107-115`；`MacRelayDriver.kt:398`。

### M2 中　hdc 目标没有与配对的那台手机绑定，USB 设备优先

- 入口：Mac 上插了别的鸿蒙设备，或 hdc 里有多台无线设备。
- 触发条件：`lib/device.mjs:131` `prefer !== 'tcp' && usb[0]` 直接选 USB；`:133` 无线侧取 `tcp[0]`，只有 USB 多于一台才报错。`/v1/target` 记下的无线地址只在多台 TCP 之间排序。
- 实际影响：〔读码〕动作和截图落到另一台设备，截图与控件树上传云端模型。
- 最小修法：配对后把手机的 `tcpAddr`（或序列号）作为必须匹配的目标写入 `target.json`，`connect()` 里选不到就报 `device_offline`，不回退到别的设备。
- 证据：`lib/device.mjs:123-133`。

### M4 中　`launch` 的 `uri` 参数：任意 scheme、明文入日志，且 App 从不使用

### M5 中　幂等 id 不绑定请求内容与路径

- 入口：`X-Request-Id` 重放。
- 触发条件：〔实测 A2〕同一个 id 先发 `click`、再发 `key home`，第二次返回第一次的结果且设备只执行一次；用同一个 id 发 `/v1/launch` 也拿到 click 的响应体。
- 实际影响：App 用 UUID，不会碰撞；任何以计数器或任务号生成 id 的客户端，在 60 秒内会把新动作静默吞掉并收到「成功」。
- 最小修法：缓存键改为 `sha256(path + body)` 加 id，同 id 异内容返回 422。
- 证据：`lib/relay.mjs:258-278`。

### M6 中　解包后的引擎代码树可写，完整性只在安装时校验一次

- 入口：任何以 App uid 运行的代码（模型的 shell、插件）。
- 触发条件：`RuntimeInstaller` 只校验 `rootfsSha256`（且该字段为 null 时跳过，`:79-84`）；manifest 里的 `jniLibs.sha256`、`bionic.nativeAddons`、`build.nodeSha256` 只写不验，启动时只比 `rootfs.version`。`BionicLaunch` 的 PATH 把 `<rootfs>/opt/dsh-app/bionic/bin` 放在 `/system/bin` 之前，该目录与 `opt/dsh/node_modules` 都可写。
- 实际影响：〔推断〕一次被攻破的会话可在 `dsh-app-boot`、`system.node` 或 PATH 前置目录里留下后门，重启后继续生效，直到运行时版本变化才被重装覆盖。glibc 世界同类问题存在，但那里的 rootfs 在 PRoot 内。
- 最小修法：启动时校验 `system.node` 与关键入口文件的哈希（manifest 已有 `nativeAddons`）；`rootfsSha256` 缺失时构建失败；PATH 前置目录改只读（安装后 `setWritable(false)`）。
- 证据：`RuntimeInstaller.kt:79-84`；`runtime/lib/rtbionic.py:306,328-333,367`；`BionicLaunch.kt:62`。

### M7 中　hdc 回显的子串匹配会把含 `offline` 的应用名判成设备离线

- 入口：`launch` 或 `bm dump -n` 一个名字含 `offline` 的 bundle（如 `com.example.offlinemaps`）。
- 触发条件：〔实测 A1〕设备回显前 200 字符含 `offline`，`hdcLevelFailure` 返回 `device_offline`，`Device.shell` 同时 `markStale()` 并把状态置 `offline`。
- 实际影响：对这类应用 `launch` 永远失败，状态页误报设备离线，下一次请求触发重连探测与 `rm -rf /data/local/tmp/dsh-relay`。
- 最小修法：只在回显以 `[Fail]` 或 `[E00xxxx]` 开头时判 hdc 层失败，去掉 `offline` 与 `Connect.*fail` 的裸子串。
- 证据：`lib/device.mjs:33`；A1 输出 `A1 -> device_offline offline`。

### L1 低　令牌无过期、无轮换，`revoke ''` 撤销全部

- `lib/auth.mjs:134` 的 `startsWith(which)` 对空串恒真，管理口（需控制令牌）传 `{id:""}` 清空所有令牌。令牌创建后永久有效，手机丢失只能靠人在 Mac 上 `revoke`。修法：`revoke` 要求 `which` 长度 ≥ 4 或精确匹配；令牌加 90 天滑动过期。

### L2 低　局域网任意主机可烧掉有效配对码

- 〔实测 A7〕同一来源 5 次形状正确的错误 `proof` 后配对码作废（`lib/auth.mjs:104-110`），随后合法配对返回「无有效码」。`no_active_code` 与 PBKDF2 路径的耗时差还能让攻击者探知配对窗口何时打开。码熵 50 位，5 次尝试，暴力破解不可行。修法：尝试计数按来源 IP 分开；无有效码时也做一次等价耗时的 KDF 或统一延迟。

### L3 低　`firstText` 对原始树递归无上限，布局极深时 observe 500

- 〔实测 A3〕1000 层正常；5000 层、20000 层触发 `RangeError: Maximum call stack size exceeded`，整次 observe 返回 `internal`。需要前台应用自己生成数千层布局，只影响可用性。修法：`firstText` 加深度参数，与 `MAX_DEPTH` 同限。证据：`lib/observe.mjs:17-26`。

### L4 低　内部错误日志带出 dump 的片段

- 〔实测 A6〕dump 不是合法 JSON 时，`msg` 字段含 `...ndows": [ SECRETPASS...`，即屏幕内容约 10 个字符。违反「日志不落控件树文字」。修法：`internal_error` 只记异常类名与固定文案。证据：`lib/relay.mjs:525`。

### L5 低　监听范围含 100.64.0.0/10 的任意网卡

- `lib/net.mjs:35-51` 把 CGNAT 段当 Tailscale 放行；Mac 经运营商 CGNAT 或手机热点获得 100.64 地址时，同网段主机可连 8731（仍需令牌或配对码）。修法：只在 `tailscale0` / `utun` 接口名上监听该段。

### L6 低　自动回退可被插件自杀触发，永久切到 bionic

- `fellBack` 条件是「glibc 子进程以 159 退出且未 ready」（`EngineFamily.kt:68-70`、`RuntimeController.kt:881`）。启动期加载的插件调用 `process.kill(process.pid, 'SIGSYS')` 即可写入回退标记，该 glibc 运行时版本之后一直走 bionic。不会形成 159 死循环：回退后 `running == BIONIC`，`shouldFallBack` 为 false，走普通失败分类与安全模式。修法：回退前先跑一次 `runProbe`，探针为 `OPEN` 则不回退。

### L7 低　`--expose-internals` 随 execArgv 传给 fork 出的子进程

- `process.execArgv.includes('--expose-internals')` 为真时，`internalModules()` 直接 `require('internal/...')`。glibc 世界里同样的能力来自 `node-addon-require-builtin` 平台包，净增风险有限；差别是 bionic 世界里所有 `fork`/`Worker` 默认继承该标志。`dsh` 包装脚本带该标志，`node` 包装脚本不带，所以模型 shell 里直接跑 `node` 拿不到。修法：插件子进程 fork 时显式传 `execArgv: []`；文档注明。

### L8 低　act 成功以输出含 `No Error` 判定

- `lib/relay.mjs:182`。〔实测 A10〕假设设备回显里同时含错误文字与「No Error」子串，仍返回 200。真实 uitest 失败文案是否回显参数未测。修法：改为整行匹配 `^No Error$`。

## 五、未能静态验证、需要真机或后续确认

1. H1 的读取路径未在真机演示；演示用例：在引擎里执行 `cat` 令牌文件。
2. 容器内 `isKeyguardLocked`、`isInteractive` 在手机亮屏、锁屏、切到鸿蒙原生应用时的取值，决定 `isLocked()` 的「或」会不会把合法操作全拒（R3、R13）。
3. 密码框已输入内容时 dump 的 `text` 是掩码还是明文（H3）。
4. `com.ohos.systemui` 是否真是下拉通知与控制中心的承载 bundle，需在真机下拉后 dump 核对（H2）。
5. 空闲连接耗尽：〔实测〕在 `ulimit -n 256` 的假设下对测试实例保持 400 条未发 ClientHello 的 TCP 连接，随后合法 `ping` 仍返回 200，未复现拒绝服务；`ulimit` 是否真正作用于该进程、launchd 下的默认软限制未核实，不列为发现。
