# P1 架构方案：引擎部分（bionic Node 子进程）

基线：dsh-go `main` 8fe1c1c，引擎 DSH 0.2.1-rc.4，Node 24.22.1，目标机 HUAWEI Pura X 卓易通容器。日期：2026年11月02日。

证据标记：〔读码〕读了源文件；〔实测〕本次在本机执行并看到输出；〔推断〕由前两者推出、未执行；〔P0A〕〔P0B〕〔P0C〕引用前序报告的章节。引用格式 `文件:行号`，引擎树文件写作 `engine:包名/路径`（rc.4 树，本次用 `runtime/locks/dsh-0.2.1-rc.4/package-lock.json` 在本机 `npm ci` 还原）。

## 0. 结论

1. 卓易通上的引擎形态是「bionic 版 Node 可执行文件由 App 当子进程 exec，跑打过补丁的 rc.4 npm 树」，作为与 PRoot、Direct 并列的第三种启动模式 `bionic`。glibc 路径一行不删，rc.4 补丁产物逐字节不变。
2. 这个模式在「物理路径世界」里运行：`HOME`、`DSH_HOME`、会话 cwd 都是 `<filesDir>/runtime-bionic/rootfs/...` 的真实路径，不做 `/root` 映射，不加载 Direct 的 `preload.mjs`。依据：Direct 自己已经把模型可见的路径改成物理路径（`GuestSetup.kt` 的 Direct 分支改写 `/root/workspace`），子进程 shell 里本来就看不到 `/root`。
3. 新增 Kotlin 类 `BionicProcess`（与 `DshProcess` 并列、不重构它）、`BionicLaunch`、`EngineFamily`、`GuestPaths`；`RuntimeInstaller` 参数化出第二个 baseDir，复用 `TarExtractor`、`ParallelXZInputStream`、`activateRootfs`、`retireRuntime`；`L2sMigration`、`DirectLaunch`、`GuestSetup.writeResolvConf` 在该模式整块不走。
4. 引擎侧只需 3 个补丁点和 3 个平台包：`dsh-app-boot` 的 `internalModules()`（走 `--expose-internals`，不编 `node-addon-require-builtin`）、`node-addon-system` 的 `flock.js`（放行 android + NDK 编 `system.node`）、`@vscode/ripgrep-android-arm64`（先试官方 linux-arm64 静态 rg，S11 不过再换）。补丁放在新目录 `runtime/patches/bionic/`，pins 另立。
5. UV_USE_IO_URING 不需要：NDK 构建下 libuv 1.52.1 在 `uv__use_io_uring()` 第一行就返回 0（`deps/uv/src/unix/linux.c:455-458`，`__ANDROID_API__` 经 NDK clang 预处理确认已定义〔实测〕）。
6. 体积：打补丁并裁剪后的 npm 树 188 MB / 13,882 个文件，tar.xz 25.1 MiB〔实测〕；pnpm 树 23 MB；node 可执行文件由 T1 给出（P0A 估 75–85 MB〔推断〕）。
7. 真机第一天跑的冒烟是 17 项（第 8 节），前 11 项只依赖 T1 的 node 可执行文件，通过扩展 P0-B 的探针 APK 执行，不等 Kotlin 启动模式。

## 1. 口径与边界

- 已钉死：不走 PRoot、不用 rootfs；白名单对主进程与 exec 子进程一视同仁，被杀的是 glibc 启动必调的 `set_robust_list(99)`、`rseq(293)` 和 io_uring、openat2、faccessat2 等共 222 个号〔P0B 一、四〕。
- 手机操控通道不在本棒。接口层只有一点：`PhoneGuest.PATCH_YAML` 的 stdio 中继以 `command: !!js process.execPath` 起子进程（`PhoneGuest.kt:55-70`），bionic 模式下 `process.execPath` 是真 node，传输方式、`relay.cjs` 逻辑都不改；只需要 YAML 里的两个 guest 绝对路径换成物理路径（第 3.7 节）。
- 本期不做不打扰模式、不做 HDC 通道、不做 x86_64 的 bionic 包（`x64` flavor 仅留 glibc，用于模拟器）。

## 2. 主要矛盾与设计决定

主要矛盾：glibc 世界（PRoot/Direct）在卓易通起不来，需要并列加一个 bionic 世界；两个世界在「路径」和「子进程」两处不兼容：glibc 世界有 guest 路径与完整 Ubuntu 用户态，bionic 世界只有物理路径与 `/system/bin` 的 toybox。

| 决定 | 内容 | 依据 |
|---|---|---|
| D1 物理路径世界 | bionic 模式不映射路径，所有写给引擎和模型的文本里的 guest 前缀（`/root`、`/opt/dsh-app` 等）在写出时经 `GuestPaths` 换成物理路径 | 〔读码〕`GuestSetup.kt` Direct 分支同样改写；`runtime/direct/paths.mjs` 的映射只服务老会话；shell 子进程看不到 `/root` |
| D2 并列的安装根 | `filesDir/runtime-bionic/` 独立于 `filesDir/runtime/`，版本标记、staging、home.carry、reset 全部各自一套 | 〔读码〕`RuntimeInstaller.kt:30-36` 与 `activateRootfs`、`retireRuntime` 都以 baseDir 为单位 |
| D3 补丁另立目录 | `runtime/patches/bionic/*.diff` + 自带 `pins.json`，与 `runtime/patches/` 的 15 个补丁串联应用 | 〔实测〕`rtbuild.py patch-dsh` 在 macOS 上对 android 过滤后的 rc.4 树应用现有 15 个补丁全部通过 pins 校验；`patch-dsh` 只读 `--patches` 目录的直接子级 `.diff`（`rtbuild.py:328-409`），子目录不会被现有构建扫到 |
| D4 并列类、不重构 | `BionicProcess` 复制 `DshProcess` 的 pump / waiter / token / ready 尾部（约 120 行），共用 `RuntimeProcessOwnership`；`DshProcess` 只增加实现同一接口 | `DshProcess.start()` 的前 90 行是 PRoot argv 装配，拆分有回归风险，非卓易通手机必须真机复验（`AGENTS.md` 真机验证条）；这是第二处重复，第三处出现时再抽 |

## 3. 启动链

### 3.1 模式选择（`EngineFamily`）

两个 family：`glibc`（现有 PRoot / Direct，内部选择不变）与 `bionic`。

选择顺序（先到先得）：

| 序 | 来源 | 说明 |
|---|---|---|
| 1 | 开发者选项三态 `auto / glibc / bionic`，存 `RuntimeController` 的 prefs 键 `engine_family_override` | 位置：诊断页开发者选项，与 `DirectEngineSettings` 并排（`app/lib/ui/settings/diagnostics_page.dart:152`）。只在引擎停止时可改，规则同 `setDirectEngine`（`RuntimeController.kt:166-171`） |
| 2 | 回退标记 `engine_family_auto_bionic`：值为触发回退时的 glibc `runtimeVersion` | 与 `K_DIRECT_FAILED` 同机制（`RuntimeController.kt:152-157`）：runtime 版本变了才再试 glibc |
| 3 | 自动判据 `confined = seLinux || syscallProbe` | 见下 |
| 4 | 默认 glibc | |

自动判据的两个信号：

- `seLinux`：`/proc/self/attr/current` 以 `u:r:aoco_untrusted_app` 开头。实测值为 `u:r:aoco_untrusted_app_27:s0:c93,c256,c512,c768`〔P0B 二，实测，n=1 台设备；读取路径〔推断〕〕。无需 exec，首屏可同步取。
- `syscallProbe`：执行 jniLibs 里的 `libdsh_sysprobe.so`（NDK 编，约 10 KB），它 fork 一个子进程调用裸 `syscall(99, 0, 0)`，父进程用 `waitpid` 看是否 SIGSYS，用自己的退出码回报（0 放行 / 42 SIGSYS / 其它未知）。直接测问题本身，厂商改名、容器版本换了仍成立。结果连同 `Build.FINGERPRINT` 缓存到 prefs，指纹变化（系统升级）后重测。代码从 `tooling/zhuoyitong-probe` 现成的 fork + raw syscall 逻辑抽取〔P0B 三〕。

`Build.FINGERPRINT` 含 `HWVDE`〔P0B 二〕只写进诊断，不参与决策：它是单机型字符串，同一容器在别的华为机型上不成立。

自动回退：glibc 模式未就绪就以 SIGSYS 退出时，写回退标记，发 notice，安装 bionic 包并重启，不计失败、不进安全模式。判定条件：`kind == LAUNCH_FAILED && exitCode == 159（128+31）&& readyAt == null`。现有 `CrashClassifier.classify` 只在 `directEngine && exitCode == SIGSYS_EXIT` 时给出该摘要（`CrashClassifier.kt:94-109`），要放宽到 PRoot；PRoot 下 tracee 被 SIGSYS 杀时 proot 的退出码未知〔推断：沿用 128+sig；备选信号是 proot 输出的 `terminated with signal 31` 行〕，用冒烟 S17 标定后再写进分类正则。

时机：`RuntimeController` 构造时确定 family（`installer` 由 `by lazy` 改成 `@Volatile var`，依据当前 family 创建），否则首屏「本机」卡片显示的体积和 `phase` 都会按错的包计算。判据 `syscallProbe` 在 worker 线程跑，结果出来前 `status.engineFamily` 先按 `seLinux` 给值，不阻塞 UI。

### 3.4 环境变量

由 `BionicLaunch.plan` 在 `env.clear()` 之后逐项放入（顺序：固定项 → `launch.env` → 调用方传入的 `pendingEnv` → `PerformancePolicy` 结果；后者覆盖前者，规则同 `DshProcess.kt:150-151`）。`launch.env` 与调用方的值都展开 `{ROOTFS}` 等占位符：`PerformancePolicy` 的 `NODE_OPTIONS` 由 manifest 原串加堆上限派生，不展开就会把 `{ROOTFS}` 原样带进引擎。

| 变量 | 值 | 理由 / 来源 |
|---|---|---|
| `HOME` | `<rootfs>/root` | Node `os.homedir()` 与 pnpm 都读它；目录结构沿用，`LastKnownGood`、`SafeMode`、`ResetKeep` 都按 `root/.dsh/...` 相对 rootfs 工作〔读码〕 |
| `DSH_HOME` | `<rootfs>/root/.dsh` | 同 Direct：`DirectLaunch.kt` 的 `directEnv["DSH_HOME"]` |
| `TMPDIR` | `<rootfs>/tmp` | Node `os.tmpdir()` 读 `TMPDIR`；libuv 在 Android 的缺省 `/data/local/tmp` 对 App 不可写〔推断〕。S9 验证可写 |
| `PATH` | `<rootfs>/opt/dsh-app/bionic/bin:/system/bin:/system/xbin` | 第一段放 `node`、`bash`、`pnpm`、`pnpx`、`dsh` 包装脚本（3.5）；`/system/bin` 提供 toybox |
| `SHELL` | `/system/bin/sh` | `subprocess-local` 的终端缺省 shell 读 `process.env.SHELL`（engine:dsh-subprocess-local/lib/index.js:1612） |
| `ANDROID_ROOT` / `ANDROID_DATA` | 取当前进程值，缺省 `/system`、`/data` | 与 `DshProcess.kt:147-148` 相同 |
| `DSH_GO_RUNTIME_ROOT` | `<rootfs>` | `RuntimeProcessOwnership.scan` 读子进程 `environ` 里的这个标记认领残留进程（`RuntimeProcessOwnership.kt:100-101`），`owned()` 再按 cwd / argv 兜底（`:112-118`）；bionic 进程的 cwd 在 rootfs 内，两路都命中 |
| `TZ` | Java 时区 id | `RuntimeController.kt:326` 已写入 |
| `NODE_OPTIONS` | `--dns-result-order=ipv4first --import {ROOTFS}/opt/dsh-go/bionic/link-fallback.mjs`，`PerformancePolicy` 追加 `--max-old-space-size=N` | DNS 顺序沿用 PRoot 模板；硬链接回退必须走 `NODE_OPTIONS`，引擎的 Worker 都以 `execArgv: []` 启动，argv 上的 `--import` 进不去（见第 11 节决定 7）；`--expose-internals` 不能放进 `NODE_OPTIONS`（`src/node_options.cc:729` 该选项无 `kAllowedInEnvvar`〔读码〕），且 `process.execArgv` 不含 `NODE_OPTIONS`，所以必须在 argv |
| `UV_THREADPOOL_SIZE` | `PerformancePolicy` 给出 | 不变 |
| `pnpm_config_registry` / `pnpm_config_package_import_method` / `npm_config_package_import_method` | 见 manifest | 前者同 PRoot 模板（`rtbuild.py:1311-1323`）；`copy` 同 Direct 的 `preload.mjs`，避免硬链接在共享存储 FUSE 上被拒（`fs-create-exclusive.diff` 针对的同一问题） |
| `LANG`、`TERM` | `C.UTF-8`、`xterm-256color` | 与 PRoot 模板一致；bash 工具自己覆盖 `TERM=dumb`（engine:dsh-bash-local/lib/index.js `ENV_OVERRIDES`） |

不设置的变量：

- `LD_LIBRARY_PATH`、`LD_PRELOAD`：node 可执行文件的 NEEDED 只有 bionic 的 libc / libm / libdl / liblog（`audit-libnode.sh` 校验项），不需要；`env.clear()` 后不放回 `LD_LIBRARY_PATH`，避免 `nativeLibraryDir` 里的库被 `/system/bin` 下的子命令加载〔推断〕。
- `UV_USE_IO_URING`：见 3.6。
- `NARB_DISABLE_NATIVE_CACHE`：只对 `node-addon-require-builtin` 的原生缓存有意义，本方案不加载该 addon。
- `LD_LIBRARY_PATH` 以外的 `PROOT_*`：不适用。

### 3.5 包装脚本与启动命令

`BionicLaunch.prepare(rootfs, nativeLibDir)` 每次启动在 `opt/dsh-app/bionic/bin/` 幂等写入（写法照 `DirectLaunch.write`，需要把它从 `private` 改为 `internal`）：

| 脚本 | 内容 | 谁会调用它 |
|---|---|---|
| `node` | `#!/system/bin/sh` + `exec '<nativeLibDir>/libdsh_node.so' "$@"` | 引擎里 `spawn("node")`、pnpm 的生命周期脚本、`SafeMode.PLUGINS_SCRIPT` 的 `cp.spawnSync('dsh', ...)` 间接调用 |
| `bash` | `exec /system/bin/sh "$@"` | bash 工具硬编码 argv `["bash","-c",cmd]`，经 PATH 查找（engine:dsh-bash-local/lib/index.js:140-145；engine:dsh-subprocess-local/lib/index.js:1523-1546） |
| `pnpm`、`pnpx` | `exec node '<rootfs>/opt/pnpm/node_modules/pnpm/bin/pnpm.mjs' "$@"` | plugin-manager 的 `execa("pnpm", ...)` |
| `dsh` | `exec node --expose-internals '<rootfs>/opt/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js' "$@"` | 安全模式的 `dsh-app-plugins` 脚本、`dsh plugin ...` |

主进程不经脚本：`/system/bin/sh -c 'echo $$ > "$0" && exec "$@"' <rootfs>/tmp/dsh-web.pid <nativeLibDir>/libdsh_node.so --expose-internals ...`。`$0` 是 pid 文件，`$@` 是其后的 argv，不拼接 shell 文本，因此路径里的空格和引号不需要转义。`exec` 之后 pid 文件里的 pid 就是 node 的 pid，停止流程沿用「读 pid 文件 → SIGTERM → 5 s 后 `destroyForcibly` → `killStrays`」（`DshProcess.kt:247-271`），去掉 proot 的 SIGQUIT 分支。`java.lang.Process` 在 minSdk 26 上没有公开的 `pid()`〔推断〕，所以保留 pid 文件。

### 3.6 UV_USE_IO_URING

结论：不需要。

- Node 24.22.1 自带 libuv 1.52.1（`deps/uv/include/uv/version.h`）。`uv__use_io_uring(flags)` 的第一个分支是 `#if defined(__ANDROID_API__) return 0; /* Possibly available but blocked by seccomp. */`（`deps/uv/src/unix/linux.c:455-458`）〔读码〕。
- NDK clang 预处理 `#include <unistd.h>` 得到 `#define __ANDROID_API__ __ANDROID_MIN_SDK_VERSION__` 且值为 26〔实测，`aarch64-linux-android26-clang -E -dM`〕，因此 `io_uring_setup(425)` 在 bionic 构建里不可达。
- 对照：非 Android 的 Linux 构建里，事件循环初始化会在 `linux.c:651` 无条件走 `uv__iou_init(..., 0)`，且环境变量 `UV_USE_IO_URING` 只门控 SQPOLL 那一路（`linux.c:478-494`）〔读码〕。所以这个变量对任何构建都没有保护作用，现有模板里的 `UV_USE_IO_URING=0` 对 glibc 构建在卓易通上同样挡不住 425。
- 同类核对：libuv 的 `accept` 用 `accept4`（`deps/uv/src/unix/core.c` 约 94-98 行，`__linux__` 下 `# define uv__accept4 accept4`），避开被杀的 202〔读码〕。

### 3.8 崩溃分类与诊断

- `CrashClassifier` 的 `FATAL`（`dsh: startup failed` 等）是 JS 层输出，bionic 下照常出现在 stderr；T1 的补丁 0001 保证 Node C++ 层 `FPrintF(stderr)` 不再进 logcat（`runtime/android-inproc/libnode/patches/0001-debug-utils-stderr-fd.patch`）。

## 6. 子进程能力与降级矩阵

### 6.1 bash 工具在 `platform = android` 上实际怎么跑

〔读码〕链路：`LocalBashExecutor.execute` 拼 `argv = ["bash","-c",command]`（engine:dsh-bash-local/lib/index.js:140-145）→ `resolveExecutable("bash")` 按 `PATH` 逐项 `stat` + `access(X_OK)`（engine:dsh-subprocess-local/lib/index.js:1523-1546），命中 3.5 的 `bash` 包装脚本 → `spawn()` → `selectContainmentMode("ordinary")`：platform 既非 linux 也非 win32，直接 `warnFallback`（日志一条 warn）并返回 `fallback`（index.js:1584-1607）→ `spawnSubprocess`：`child_process.spawn(program, args, { cwd, env, stdio, detached: true })`（engine:dsh-subprocess-local/lib/runner-launch-B2zsQ1Dz.js:1020-1050），进程树所有权由 `fallbackOwner`（`:797-840`）按进程组管理：`kill(-pid, sig)`，`waitForExit` 轮询 `kill(-pid, 0)` 直到组内无成员，android 不走 linux 的 `/proc` 成员核查（`:811`），所以后台常驻子进程会让这一轮的 `waitForExit` 持续到它们结束或被 SIGKILL，行为同 macOS。

PRoot 模式下 platform 是 linux，先探 systemd scope 再落到同一个 fallback，实际路径相同。沙箱：android 不在 `PLATFORM_CHAINS`，`confine()` 抛 `SandboxUnavailableError`（engine:dsh-sandbox-local/lib/index.js:173-176、492-499），与现状（PRoot 里 bwrap / landlock 不可用）一致，`AGENTS.md` 已指示模型用 `danger-full-access`（`GuestSetup.kt:33-34`）。

bash 实际是 `/system/bin/sh`：Android 8+ 为 mksh〔推断〕；toybox 命令集见 P0B 二。数组、`[[ ]]`、花括号展开 mksh 支持，进程替换 `<( )`、`$'..'` 的部分用法不支持〔推断〕，S12 取 `$KSH_VERSION` 与逐项 `type` 验证。

### 6.3 作者鸿蒙分支（`origin/claude/harmonyos-ohos`，530f183）的取舍

作者那套是为「容器不允许任何子进程」写的：把 `subprocess` 与 `sandbox` 两个服务整体换成 `worker_threads` + just-bash 虚拟解释器（`runtime/ohos/process/` 共 331 KB 源码，含私有构建 just-bash 3.6.0、re2js 私有构建、isomorphic-git）。卓易通允许 exec（P0B 七），所以：

| 件 | 取舍 | 怎么借 |
|---|---|---|
| 虚拟 shell（just-bash） | 不借 | 真 `/system/bin/sh` 能力严格大于命令白名单解释器，且不增加 331 KB 的维护面 |
| 虚拟 rg（`rg.mjs`、`rg-select.mjs`、`build-rg-regex.mjs`、`regex-src/`，合计约 28 KB 源码 + re2js 1.3.3） | 备选，S11 失败且不愿装 Rust 时启用 | 把 `rg.mjs` 以 `bin/rg` 脚本（`#!/system/bin/sh` + `exec node rg.mjs "$@"`）形式提供，不必换掉 `subprocess` 服务；作者文档限定它只实现 DSH 实际消费的 JSON `match` 记录与一部分 glob / 正则语义（`README.md`「rg 范围」），需单独跑 DSH 的 grep / glob 用例回归 |
| isomorphic-git 受限 Git Worker | 本期不借 | DSH 的 `workspace-changes` 通过 `subprocess.resolveExecutable("git")` 找可执行文件；要借就得提供 `bin/git` 脚本包 isomorphic-git 的子集，先看 `workspace-changes` 实际调用的子命令再定，属后续 |
| 「明确拒绝插件安装」（`plugin-install-refusal.md`） | 不借 | pnpm 在这里可用；只对 git 来源拒绝（6.2） |
| libnode 构建经验、`host_core.cpp` 的管道 / 环境保存恢复 | 已由 T1 与 P0A 3.4 消化 | 本方案走子进程，不需要进程内宿主 |

## 11. 主线决定（2026年11月02日，用户授权主线自决）

1. 单个 APK 同时带 glibc 与 bionic 两套运行时，保留自动回退；P2-2 首次出包后以实际体积复核，超出 1.0.9 体积 40% 以上再议拆包。
2. 第 6 节降级矩阵作为本期验收口径：git 来源插件、python 类插件、本地语音、终端、Office 转换在卓易通上本期拒绝，拒绝原因是容器内没有 git / python / curl，界面文案要说明原因而不是只报失败。
3. S11 失败时 rg 兜底借作者分支的 JS 虚拟 rg，不在本机装 Rust 工具链。
4. （2026年11月02日，据 P2-5 真机冒烟）`os.cpus()` 在容器内返回空数组（`/proc/stat` EACCES），引擎无调用点，不处理，只记入第 6 节降级矩阵；S11 官方 linux-arm64 静态 rg 15.0.0 实测可用，决定 3 的 JS 虚拟 rg 兜底不启用。
5. （2026年11月02日，据 P3 真机「新建对话失败」）第 2 节第 2 条「bionic 不做 `/root` 映射」的依据不成立：Direct 模式除了把模型可见路径改成物理路径，还由 `runtime/direct/preload.mjs` 在引擎的类型化边界（`zz-direct-runtime.diff`，`Symbol.for("dsh.go.direct")`）把 Dart 客户端与会话元数据里的 guest 路径（`/root/workspace`、`/root/.dsh`、`/tmp`、`/opt/dsh*`）映射成物理路径；bionic 没装这个适配器，`session/create` 的 cwd `/root/workspace` 原样进引擎，`mkdir` 失败。修法是运行时层新增 `runtime/bionic/{paths,preload}.mjs`，打进归档 `opt/dsh-go/bionic/`，`launch.argv` 在 `--expose-internals` 后加 `--import {ROOTFS}/opt/dsh-go/bionic/preload.mjs`；适配器只改写与 Kotlin `GuestPaths.MAPPED` 相同的八个 guest 前缀，`/sdcard`、`/system`、`/data` 原样放行，子进程不接管（`command` 返回 undefined）。Dart 与 Kotlin 主逻辑不动。测试 `runtime/tests/bionic-paths.test.mjs`（含前缀表与 Kotlin 对拍、真实 `--import` 加载）。
6. （2026年11月02日，据 P5 深度审查）路径边界补齐到四处：`dsh-workspace` 的 `realpathNormalize`、`dsh-api-workspace-controller` 回给界面的工作区路径（过 `toGuest`）、目录选择器 `list/createDirectory`（入参 `toHost`、回程 `toGuest`）、`dsh-tool-bash` 的 `resolveWorkdir`；pins 用 `--record` 在干净树上重算，运行时版本 `bionic-r1-dsh0.2.1-rc.4-node24.22.1-536ee8aa2a40`。Kotlin 侧：`GuestFiles.rootfs()` 改取 `RuntimeController.activeRootfs`，对 rootfs 内的物理路径规范化后直接放行（引擎回给界面的工具结果与产物路径是物理路径，实跑证实）；`status()` 新增 `rootfs` 字段供 Dart 四处直读 rootfs 的代码使用；`EngineFamily.decide` 新增 `glibcBundled`，纯 bionic 包恒选 bionic（`onlyBundled`）；安装前所需空间 1.3 倍、升级再加一份旧 rootfs；安全模式辅助脚本在 bionic 下首行指向 node 包装脚本。终端 / persistent-bash 在 bionic 下不可用（`/bin/bash` 与 node-pty 无 android-arm64 预构建）记入第 6 节降级矩阵。全表见 `P5-深度审查.md`。
7. （2026年11月03日，据真机对话首轮）卓易通的 App 数据目录拒绝硬链接（`link()` 返回 EACCES），引擎的会话持久化 worker 与会话首次落盘都用 `link(暂存, 正式)` 做「目标不存在才发布」，每轮对话一开头就失败；glibc 路线有 PRoot 的假硬链接兜住。修法是 `runtime/bionic/link-fallback.mjs`：EACCES / EPERM 时改用 `copyFile(COPYFILE_EXCL)` 再 fsync，目标已存在仍报 EEXIST，经 `launch.env.NODE_OPTIONS` 加载；同时 `BionicLaunch` 对调用方环境也展开占位符。测试 `runtime/tests/bionic-link-fallback.test.mjs` 与 `BionicLaunchTest`。
8. （2026年11月03日，据真机网页版）容器里的 WebView 是华为自带 HwWebview，缺 `AbortSignal.any`、`Promise.withResolvers` 等较新内置，网页版整页卡在加载、目录选择器报错。dsh-go 桥订阅 `webserver/index-inject`，把 `lib/web-polyfills.js` 作为第一条 `<head>` 注入行，逐项检测、原生有就跳过；桥在 glibc 与远程主机上同样加载，补丁对它们无副作用。测试 `runtime/tests/bridge-web-polyfills.test.mjs`。
