# DSH Go 鸿蒙卓易通改造方案

目标机：HUAWEI Pura X（VDE-AL00），HarmonyOS 7.0.0.109，安卓应用只能跑在卓易通（`com.droi.tong` 1.0.10.93）容器里。
基线：dsh-go `main` 8fe1c1c（1.0.9），引擎 DSH 0.2.1-rc.4 + Node 24.22.1，PRoot 启动。
日期：2026年11月02日。

## 一、口径

一句话目标：在这台鸿蒙手机上，DSH Go 做到和安卓真机一样——引擎跑在手机里，手机操控能操作这台手机。

验收三条，全部在 Pura X 真机上过：

1. 首启选「本机」，不连任何电脑，引擎能启动，能完成一轮对话。
2. 开启手机操控后，给一句自然语言任务（例如「打开设置，把蓝牙关掉」），DSH Go 在鸿蒙原生界面上自己看屏、点按、输入完成它。**2026年11月02日修订**：操控的「手」经 Mac 中转——手机上的引擎把看屏与点按请求发给 Mac 上常驻的 hdc 中继，中继经 Wi-Fi 无线调试操作这台手机；Mac 必须在线。依据是 P0-B 两轮实测：容器内的 App 没有用户态手段碰到手机自己的 hdcd，安卓无障碍在容器里启用不了。
3. 网页版、插件市场、分享这些既有功能在本机模式下可用，不比遥控模式差。

本期不做：不打扰模式（后台虚拟屏）。原因：操控通道走鸿蒙调试接口 uitest，它只能作用于物理屏，容器里也没有虚拟显示能力。

已否决的方向，后面各棒不要再绕回去：

- 在现有 PRoot / 直接启动架构上打补丁。issue #24 已把 461 个系统调用逐个探过：容器对 App 拉起的子进程只放行约 40 个，`ptrace`、`clone3`、`socket` 全部是 SIGSYS 直接杀进程。改写系统调用号救得了 `/bin/true`，救不了线程和网络。
- nodejs-mobile。停在 Node 18.20.4（2024-10），引擎要 Node 24。
- 用安卓无障碍做手机操控。容器内的无障碍服务只看得见容器自己，碰不到鸿蒙界面。
- 等作者鸿蒙原生版（`claude/harmonyos-ohos` 分支）。它自述引擎「还没有在设备上跑过」，没有手机操控代码，装它还要华为开发者账号按 UDID 签名。它的 libnode 构建经验要借，整包不等。

## 二、两处架构改动

> **2026年11月02日 P0 探针后的修订。** P0-B 真机实测（`P0B-容器探针.md`）推翻了 issue #24 的归因：卓易通的 seccomp 白名单套在整个 App 进程树上（主进程、`:engine`、exec 子进程三处逐号一致），被 SIGSYS 杀的是 glibc 启动必调的 `set_robust_list`、`rseq` 以及 io_uring、openat2、faccessat2 等共 222 个号；线程、fork、exec、socket 全部放行，`clone3` 只返回 EPERM。所以第 1 项改为「**bionic 版 Node 可执行文件由 App 当子进程 exec**」，进程内 libnode 退为备选：前者 `process.execPath` 仍是真 node，现有 `DshProcess` / `DirectLaunch` 的启动、日志、崩溃分类代码可复用，手机操控的 stdio 中继与 pnpm 装插件也不用改传输方式。第 2 项的自连 HDC 在 TCP 层被实测否定（容器有独立网络命名空间却顶着同一个 IP，打 192.168.31.226:46225 与 127.0.0.1 都是 ECONNREFUSED）。第二轮探针（P0B 第九节）把剩下的路也走完了：容器实际挂在宿主桥 `ancowlan0`（172.17.1.1/24）上，打 172.17.1.1:46225 被静默丢包；容器 DNS 是路由器而非宿主，宿主对容器只做 NAT 出站、不开任何口；安卓无障碍在容器里连启用页都打不开；宿主侧 toybox 没有 nc、`/data/local/tmp` 禁止执行、shell 身份动不了 iptables，也放不下一个中继。**结论：在未 root 的 Pura X 上，卓易通里的 App 没有任何用户态手段碰到 hdcd，「手机不靠电脑自己操控自己」在这条路线上做不到。** 手机操控剩两条路：经 Mac 中转（手机上的引擎把操控指令发给 Mac 上的 hdc 中继，Mac 必须在线），或等鸿蒙原生版配上系统级输入能力。走哪条由用户定。

### 1. 引擎进 App 进程（原案，已被 1′ 取代）

现状：Kotlin 侧 `RuntimeController` → `DshProcess` exec 一个 glibc 的 Node 可执行文件（PRoot 包着 Ubuntu rootfs，或 `DirectLaunch` 直接用 glibc loader）。被杀的三个系统调用全发生在这个子进程里。

改法：把 Node 24.22.1 编成 bionic 的 `libnode.so`，由 App 自己的进程（建议独立的 `android:process=":engine"`，仍是 zygote 派生的 App 进程，崩溃不连累界面）通过 JNI 加载，在进程内启动 `dsh web`。App 进程本身能开线程、能联网，否则 DSH Go 的界面和插件市场都跑不起来。引擎的 npm 树不再放进 rootfs，直接放 App 私有目录；`runtime/patches/` 的补丁照打；六个原生扩展逐个判定：安卓有构建的就编，没有的做降级。

待探针证实的前提（P0-B）：容器那张系统调用白名单只套 exec 出来的子进程，不套 App 主进程里的原生代码。

### 2. 手机操控换通道：自连 HDC

现状：手机操控依赖安卓无障碍（读屏、点按）和不打扰模式的四条通道（root / Sui / Shizuku / 自连 ADB）。

改法：加一条「自连 HDC（鸿蒙）」通道。手机开无线调试后，App 内置的 hdc 客户端经 Wi-Fi 连本机 hdcd，做一次 RSA 配对（手机弹一次授权），之后用 `snapshot_display` 截屏、`uitest dumpLayout` 读控件树、`uitest uiInput click/swipe/inputText/keyEvent` 操作、`aa start` 拉起应用。这套命令 2026年11月02日已在 Mac 上用 hdc 对这台手机跑通一遍（装 APK 的全程）。hdc 客户端必须在 App 进程内实现（Kotlin 或 JNI），exec 出去的 hdc 二进制会在 `socket()` 上被杀。

待探针证实的前提（P0-C）：hdcd 的 TCP 模式与 RSA 认证能被非官方客户端完成；容器内的 App 能连到手机自己的无线调试端口。

## 五、风险与待拍板

1. 构建链放哪：本地装（JDK 17、Flutter 3.47.7、Android SDK、NDK，约 4–5 GB）还是 GitHub 仓库跑 Actions。本地迭代快，Node 交叉编译一次要几十分钟；Actions 省本机磁盘但每轮要推代码。
2. libnode 能否在 macOS 上交叉编成 bionic 版。作者是在 Linux 上编的 OHOS 版，Termux 也在 Linux 容器里编。编不出来就要一台 Linux（Actions 的 ubuntu runner 可以）。
3. 子进程能力缺口。容器里 exec 的子进程不能联网、不能多线程，引擎的 shell 工具、插件安装（pnpm）、git 都会受限。P0-B 出结果后定哪些功能在鸿蒙上降级。
